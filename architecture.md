# Архитектура — Money Manager

Заметка для себя: как применить hexagonal architecture, DDD и практики Владимира Хорикова на практике, без академической зауми. Цель — не просто следовать паттернам, а понимать, зачем каждый нужен.

## Как соотносятся эти термины

Легко запутаться, потому что термины пересекаются:

- **DDD (Domain-Driven Design)** — про то, *как моделировать* бизнес-логику: сущности, инварианты, язык предметной области.
- **Hexagonal / Clean Architecture** — про то, *как раскладывать код по слоям*, чтобы бизнес-логика не зависела от БД, сети, UI.
- **Практики Хорикова** — конкретные технические приёмы, которые помогают реализовать первые два пункта на практике: Always-Valid Domain Model, Functional Core/Imperative Shell, CQRS-lite.

То есть DDD — что моделируем, hexagonal — как раскладываем по файлам, Хориков — как именно писать код внутри.

## Слои проекта

```
domain/          — бизнес-логика. Не знает про SQL, HTTP, UniFFI.
infrastructure/  — реализация: rusqlite-репозитории, HTTP-клиент к серверу.
ffi/             — тонкий слой для UniFFI, вызывает domain.
server/          — Axum API, тоже вызывает domain.
```

Правило одно: `domain` ничего не импортирует из `infrastructure`/`ffi`/`server`. Зависимость идёт только внутрь.

Зачем это вообще нужно новичку в практике: если однажды захочешь заменить rusqlite на что-то другое, или добавить веб-версию — бизнес-логику трогать не придётся.

## 1. Always-Valid Domain Model

**Идея.** Объект предметной области не должен уметь существовать в невалидном состоянии — ни на секунду. Не "создали объект, потом проверили", а "невалидный объект просто нельзя создать".

**Как это выглядит в Rust.** Поля приватные, единственный способ создать объект — конструктор, который возвращает `Result`:

```rust
pub struct Money {
    minor_units: i64, // копейки/центы, приватно
}

impl Money {
    pub fn new(minor_units: i64) -> Result<Self, DomainError> {
        if minor_units < 0 {
            return Err(DomainError::NegativeAmount);
        }
        Ok(Money { minor_units })
    }
}
```

Никакого `pub minor_units: i64` и никакого сеттера, который позволит поставить туда мусор.

**Почему это непривычно на старте.** Тянет писать структуры с публичными полями "для простоты" и проверять валидность где-то в другом месте (в сервисе, в UI). Проблема в том, что тогда проверку легко забыть в одном из мест вызова. Правило: если в поле нельзя положить что попало — прячь поле.

---

## 2. Functional Core, Imperative Shell

**Идея.** Всё, что не имеет побочных эффектов (не трогает диск, сеть, время, рандом) — чистые функции в `domain`. Всё, что имеет эффекты — на границе, в `infrastructure`/`ffi`/`server`.

**Как это выглядит.**

```rust
// domain — чистая функция, никакого IO
pub fn record_transaction(
    account: &Account,
    amount: Money,
    category: CategoryId,
) -> Result<Transaction, DomainError> {
    // только бизнес-правила, никакого rusqlite здесь
    Transaction::new(account.id, amount, category)
}

// infrastructure — здесь уже есть побочный эффект (запись в БД)
pub fn save_transaction(conn: &Connection, tx: &Transaction) -> Result<(), InfraError> {
    conn.execute("INSERT INTO transactions ...", params![...])?;
    Ok(())
}
```

**Почему это ценно для тебя как для новичка в тестировании.** Функцию `record_transaction` можно протестировать без БД вообще — просто вызвал с аргументами, проверил результат. Это резко снижает порог входа в написание тестов: не нужны моки, фикстуры, тестовая БД.

**Частая ошибка новичка.** Смешивать: положить `conn.execute(...)` прямо в функцию с бизнес-правилами "для быстроты". Работать будет, но тестировать станет больно, и это первый признак, что pure/impure перемешались.

---

## 3. CQRS-lite

**Идея.** Не путать с полным CQRS (отдельные БД для чтения и записи) — это ceremony, которая тут не нужна. CQRS-lite — просто разделение на уровне кода: команды (меняют состояние, идут через доменную модель) и запросы (только читают, могут идти в обход домена напрямую в SQL).

```rust
// Команда — через domain, с валидацией
pub fn handle_add_transaction(cmd: AddTransactionCommand) -> Result<Transaction, DomainError> { ... }

// Запрос — напрямую SQL-проекция, без доменных объектов
pub fn monthly_spending_by_category(conn: &Connection, month: Month) -> Vec<CategorySpending> {
    // просто SELECT SUM(...) GROUP BY category — без Transaction-объектов
}
```

**Почему так.** Для отчётов ("траты по категориям", "баланс на дату") городить полноценные доменные объекты избыточно — это чтение, инварианты тут ни при чём, важна скорость и удобство агрегации.

---

## 4. Result вместо исключений

В Rust это и так единственный нормальный путь — `panic!` не для ожидаемых ошибок. Важное разделение:

- `Result<T, DomainError>` — ожидаемые бизнес-ошибки (отрицательная сумма, несуществующая категория). Их обрабатывает вызывающий код.
- `panic!`/`unwrap` — только там, где нарушение инварианта означает баг в самой программе, а не ошибку пользователя.

---

## 5. Тестирование

Порядок приоритетов по Хорикову: сначала много дешёвых тестов на `domain` (чистые функции, без моков), потом немного интеграционных тестов на `infrastructure` (с реальной SQLite в памяти), и по минимуму — тестов на `ffi`/`server` (там уже просто проверяешь, что адаптер правильно прокидывает вызовы).

---

## Как осваивать это практически, а не утонуть

Раз опыта с этими практиками ещё не было — важно не пытаться сделать "идеально по книжке" с первой строчки кода. Хориков сам подчёркивает прагматизм: не всякий CRUD заслуживает полного домена.

Практический порядок освоения:

1. Начни с одной сущности (например, `Transaction`) — сделай для неё Always-Valid конструктор. Это самый дешёвый и понятный шаг.
2. Раздели domain/infrastructure на уровне папок в одном crate, не сразу разными crates — physical separation можно добавить позже, когда почувствуешь, где проходит граница.
3. Функции без побочных эффектов пиши в domain с самого начала — привычка, а не рефакторинг постфактум.
4. CQRS-lite вводи только когда появится первый отчёт/агрегация — до этого нет смысла.
5. Тесты пиши сразу на domain-функции — раз они чистые, это займёт минуты, и сразу видно пользу практики.

Если где-то практика начинает мешать, а не помогать (усложняет простую вещь) — это нормальный сигнал упростить, а не знак, что "делаешь неправильно".
